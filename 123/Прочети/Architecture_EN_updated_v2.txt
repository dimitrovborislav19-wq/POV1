1. What We Actually Analyzed

We analyzed an obfuscated .NET application in which the licensing logic is not located in a single place, but is split across several layers:

local licensing/state layer
startup/orchestration layer
remote HTTP licensing client
request/response pipeline
signature/integrity seam
runtime state and UI consumers

The main conclusion is that this is not a simple license check inside one method, but a multi-stage architecture.




1.1 Scope Clarification

This is a structural architecture analysis, not a patch-vs-original comparison report.

Binary comparisons, hashes, resource checks, and runtime tests were used only as validation techniques.
Their purpose was to confirm the execution structure and to eliminate incorrect hypotheses, such as:

different entry point
missing embedded resource
modified protected resource payload
failing module constructor
early anti-tamper crash

The core goal of the analysis is to map the application architecture:

startup flow
protection/bootstrap layers
protected resource and string infrastructure
dispatcher / VM-style execution layer
normal licensing manager
local and remote licensing flows
runtime/UI consumers

Therefore, binary variant observations should be treated as supporting evidence, not as the main subject of the document.

7. Anti-Tamper and Protected Resource Bootstrap Layer

After the initial licensing architecture analysis, we also identified a separate protection/bootstrap layer.
This layer is not the same as the normal licensing manager or the HTTP licensing client.

It sits earlier and lower in the startup sequence and is responsible for:

assembly integrity validation
protected resource loading
protected string table initialization
runtime dispatcher / VM-style execution
caller validation around protected string access

This means the application has at least one additional defensive layer before or around the normal licensing logic.

7.1 Module-Level Anti-Tamper Check

The first protection point observed was the module initializer path.

Observed runtime failure:

<Module> .cctor()
  -> tcluRCmJ2u79OhTbGG.fXUU4jykVT4coaAMg9aB.gRpykFhmKaB()
  -> System.Exception: PVSOLpremium is tampered.

Meaning:

the application performs an early module-level integrity check
the check runs before the normal application entry point
when the executable is modified, the check detects the change
the application terminates with an explicit tamper message

Important conclusion:

This is not a normal business exception.
It is an explicit anti-tamper failure path.

The relevant method is:

fXUU4jykVT4coaAMg9aB.gRpykFhmKaB()

The method contains an explicit failure path that builds the message:

<AssemblyName> is tampered.

In the observed case, this became:

PVSOLpremium is tampered.

7.7 Meaning of the Second Crash

The second crash is different from the explicit:

PVSOLpremium is tampered.

Instead, it is a generic:

System.Exception

inside the protected dispatcher.

The important point is that later validation narrowed this down structurally.

Runtime validation showed:

the protected manifest resource exists
the protected manifest resource is not null
the protected manifest resource has the same length in the observed binary variants
the protected manifest resource has the same SHA256 hash in the observed binary variants
the module constructor succeeds
the managed entry point is the same

Observed protected resource:

uNs7Wte18A4oyf6jm5.SPbLiIyKtHBSsv8DfR

Observed resource length:

263,168 bytes

Observed resource SHA256:

b69aa599274d818416707a40e44d164690267d8f390bbfcf89b5872ced84dc9a

Therefore, the second crash is not explained by:

missing embedded resource
null resource stream
different raw protected resource payload
failure in <Module>.cctor()
different managed EntryPoint

Updated interpretation:

The second crash is most likely caused by one of the following structural conditions:

A) Dispatcher / VM runtime state mismatch

The protected dispatcher may depend on runtime state initialized outside the raw resource payload.

B) Metadata or method-body dependent protection

The dispatcher may depend on stable metadata tokens, method bodies, RVAs, section layout, internal tables, or module-level state.

C) Bootstrap side-effect dependency

The module-level protection method may do more than validate integrity.
It may initialize state required by the protected string/resource loader.

D) Secondary fail-closed behavior

The first layer can produce an explicit tamper message.
The second layer appears to fail generically through System.Exception, likely to avoid exposing internal protection details.

Important conclusion:

The protected resource exists and is byte-identical in the observed checks.
The crash therefore belongs to the protected dispatcher/bootstrap state layer, not to simple resource absence.

7.10 Updated Main Conclusion

The application uses a multi-layer defensive design.

The licensing system is not protected only by business-level checks.
It is surrounded by lower-level protection mechanisms:

early module integrity validation
protected embedded resources
lazy string decoding
dispatcher / VM-style invocation
caller assembly validation
generic fail-closed exceptions

Therefore, any analysis of the licensing architecture must separate:

normal licensing logic

from:

protection/bootstrap infrastructure

These are related at runtime, but architecturally they are different layers.
